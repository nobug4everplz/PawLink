# 資料庫設計決策紀錄

使用者 2026-11-11 授權由 Claude 代為決定需組內討論的事項，以下為已定案內容，組內如有異議可再提出修改。

| # | 決策 | 理由 |
| --- | --- | --- |
| D1 | 第一階段第 7 張表為 `animal_photos` | 計畫只列 6 張；FR-1.4 需要多張照片，獨立成表方便封面照片與刪除管理 |
| D2 | 「照顧者」以餵食點為單位（`spot_caretakers`），不是全域角色；建點者自動成為該點 `owner`，其他登入者可自行加入為 `caretaker` | 同一人可能只照顧部分點；權限可精準到「只能改自己照顧的點」 |
| D3 | `profiles.role` 只有 `user`、`admin`；角色只能由管理員以 `set_user_role()` 設定 | 防止自己升權 |
| D4 | TNR 五階段：1 未結紮、2 誘捕中、3 已手術、4 術後照護、5 已原地回置；第 3 階段起自動標記「已結紮」（`is_sterilized`），不可手動改 | 結紮標記是必保功能，由階段推導可避免兩個欄位不一致 |
| D5 | 訪客位置吸附到 TWD97 100 公尺網格中心（最大偏移約 71m），範圍篩選也用模糊位置；訪客看不到描述、看不到誰餵的 | NFR-1；固定吸附可防多次查詢平均回推 |
| D6 | 腳印顏色：6 小時內綠、6～24 小時黃、超過 24 小時或沒紀錄紅 | 依計畫 FR-1.3 的 6／24 小時門檻 |
| D7 | 餵食點以「停用」取代刪除，只有管理員可真正刪除 | 保留歷史餵食與清理紀錄 |
| D8 | 離線補傳最多接受 7 天前的紀錄，前端以 UUID 去重 | FR-1.5；避免誤植很久以前的時間 |
| D9 | 三層警示是「提醒並要求再確認」，不是硬性禁止：紅色（熱區內）與黃色（200 公尺內）建點前都要再按一次確認 | 計畫寫的是警示；示意圖資不夠精確，硬擋會誤傷。管理員可在後台看到落在熱區內的點再處理 |
| D10 | 保育熱區對所有人公開（含訪客），並用 `is_demo` 標示「示意資料」，預設為示意 | 沒有官方圖資，依公開文獻自行繪製的大範圍必須標明；熱區是大範圍，不會洩漏動物確切位置 |
| D11 | 熱區一次只收一個多邊形，上限 500 個頂點、10,000 平方公里；自我相交由資料庫 `ST_IsValid` 擋下（RPC 與資料表 CHECK 兩層） | 計畫的完成條件；資料表層再擋一次，繞過 RPC 也寫不進去 |
| D12 | 動物建檔時以所屬餵食點的位置檢查警示；紅色且動物尚未結紮才要求再確認 | 動物身分檔本身沒有座標；熱區內最該優先處理的是未結紮個體 |
| D13 | 後台另外做了餵食點管理（停用／啟用、指派 owner）；至少保留一位管理員 | 補上階段 1 留下的「最後一位 owner 退出後沒人能管」；避免管理員全部被降級後無人能進後台 |
| D14 | 宣導頁的文字與外部連結集中在 `src/lib/conservationContent.js`；捐款只放對方官網連結，平台不經手金流 | 組員可直接改文案；免去金流與收據責任 |
| D15 | 居民匿名干擾通報依計畫屬於階段 3，階段 2 不做 | 計畫第 2、4 節都把 FR-2.1／2.2 排在階段 3，需要 Turnstile 與頻率限制，另開一輪 |
| D16 | 匿名通報的頻率限制與 Turnstile 驗證都做在資料庫函式裡，不另外寫 Edge Function | 只要在 SQL Editor 執行 migration 就能上線，不需要 Supabase CLI 部署；secret 放在前端讀不到的 `private.app_secrets` |
| D17 | Turnstile 是選配：沒設定 secret 時只靠頻率限制，設定後才強制驗證 | 需要組員申請 Cloudflare 帳號；沒申請前功能照樣可用，完成條件「短時間重複送出會被擋」由頻率限制達成 |
| D18 | 頻率限制：同一來源 60 秒 1 則、同一點 10 分鐘 1 則、1 小時 3 則；單一餵食點 1 小時 10 則。來源以 IP 加鹽雜湊辨識，不存原始 IP | 擋灌水又不留下可辨識通報人的資料。同一個 Wi-Fi 的人會共用額度，屬已知取捨 |
| D19 | 通報不收任何聯絡方式；內容只有該點照顧者與管理員可讀 | 匿名才敢通報；避免平台持有居民個資 |
| D20 | 進度公開只顯示通報類別、狀態、時間與照顧者的回覆，不顯示通報內容 | 內容可能寫到人名或門牌。回覆欄位在介面上明講「會公開」 |
| D21 | 站內通知做成地圖頁的「居民通報」數字與收件匣，不做推播 | 計畫風險表已定：一律先做站內通知，Web Push 列選配 |
| D22 | 交流空間做到發文、留言、檢舉；只有登入者可讀；同一則內容 3 人檢舉自動隱藏，管理員在後台決定隱藏或駁回 | 計畫第 4 節的完成條件是「登入者可發文，可檢舉」；自動隱藏讓管理員不在時也有基本防護 |
| D23 | 留言送出後不能修改，只能刪除；每人 1 小時最多 5 篇貼文、30 則留言 | 避免被檢舉後改內容規避；基本的洗版防護 |
| D24 | 預設保育熱區 5 處（苗栗、臺中、南投石虎，金門歐亞水獺，臺北富陽穿山甲）以 migration 0008 寫入，全部標示意 | 林保署物種頁點名的主要族群地與犬貓威脅；拿不到官方棲地圖資，石虎與水獺改用鄉鎮界線（內政部界線，taiwan-atlas 簡化）劃定，富陽為手繪，來源寫在各熱區說明 |
| D25 | 宣導頁物種擴充為 7 種，保育等級依 2025-02-07 修正的陸域保育類野生動物名錄；外部連結只放確認打得開的官方網站 | 原本的石虎保育協會網址查不到是否正確，先拿掉；看到正確官網再加回 `conservationContent.js` |
| D26 | 離線打卡只支援「記錄餵食」；建點、動物建檔、清理回報離線時不能做 | 計畫 FR-1.5 的範圍就是打卡；其他操作需要伺服器即時檢查（30 公尺重複點、保育警示、權限） |
| D27 | 離線紀錄存在手機的 IndexedDB，建立當下就產生 UUID；恢復連線、回到前景、重新開啟時自動補傳。被伺服器拒絕的紀錄（餵食點已停用、超過 7 天）直接放棄並告知 | 伺服器以 UUID 去重，重送幾次都只有一筆；被拒絕的重送也不會成功，留著只會卡住佇列 |
| D28 | 離線時地圖顯示「上次載入的餵食點」（存在 localStorage，最多 600 個，登出時清除）；離線不做 2 小時重複投餵提醒 | 沒網路查不到別人剛才有沒有餵過；登入者拿到的是精確位置，登出後不留在手機上 |
| D29 | Supabase 的 API 回應不放進 service worker 快取；只快取 App 外殼、看過的地圖圖磚（400 張、7 天）與動物照片 | 權限相關的資料不該留在共用快取裡被下一個登入的人看到 |
| D30 | 哨兵的「最後出現」以建檔時間起算，之後只由目擊回報更新；記錄餵食不算看到動物 | 餵食的人不一定看到每一隻；決策表 3 也把「有人餵過」和「有沒有被看到」分開當條件 |
| D31 | 門檻 T＝max（3 天，平均出現間隔 × 2）照 M1 決策表 3；平均間隔取最近 10 次目擊，不到 2 次就用 3 天；「超過」是嚴格大於 | 只看最近的紀錄，習慣改變時門檻會跟著變；剛好等於門檻不算超過 |
| D32 | 「這段期間該點有人餵過」＝動物出沒的任一個啟用中餵食點，在牠最後出現之後有餵食紀錄。提醒掛在最近一次餵食的那個點 | 沒人去過就沒人有機會看到牠，不能說牠不見了（規則 4） |
| D33 | 同一次「沒出現」只提醒一次：照顧者結案後不再提醒，要等牠再被看到、之後又超過門檻才會發新的提醒 | 每天都跳同一則提醒會被當成雜訊；決策表規則 3 只說「已有未處理的提醒不提醒」，這是補上結案之後的行為 |
| D34 | 健康提醒不重複開：同一隻動物已有未處理的健康提醒時，新的受傷／跛腳／消瘦回報更新同一則 | 三個人回報同一隻跛腳的貓，照顧者只需要看到一則 |
| D35 | 提醒只給該動物出沒點的照顧者、建檔者與管理員看；所有登入者都能回報目擊與看目擊紀錄，訪客只看得到「最後出現」時間 | 沿用動物身分檔的編輯權限判斷；目擊紀錄不含精確位置 |
| D36 | 哨兵不會自動把動物改成「失蹤」，由照顧者在結案時決定是否標記；標記為失蹤的動物被回報目擊後自動恢復，並解除失蹤提醒 | 提醒只是「可能」失蹤，判斷留給認識這隻動物的人 |
| D37 | 每日檢查用 pg_cron，臺灣時間 04:00；管理員可在後台「哨兵」分頁手動執行，並看到排程有沒有啟用 | 計畫指定 pg_cron；手動執行讓 Demo 不用等到隔天，也是排程沒啟用時的備案 |
| D38 | 目擊回報頻率限制：同一人對同一隻 10 分鐘 1 次、每人 1 小時 30 次；只能回報 7 天內的目擊 | 基本的洗版防護；太舊的目擊對哨兵沒有意義 |
| D39 | 輪值：一個餵食點每天早上、晚上各一班；只有該點的照顧者可以排班與代班；可登記今天起 30 天內 | M1 資料字典的時段就是 morning／evening；班表是照顧者之間的分工，不對外公開 |
| D40 | 「同一人同時段不可重複排班」跨餵食點計算，自己排的和代別人的都算；班被代走之後原排班者該時段就空出來 | 一個人同一時段只能出現在一個地方（處理 2.3、決策樹的時段衝突） |
| D41 | 代班認領用資料列鎖：先鎖住那一班再檢查狀態，兩人同時按只有第一個成功，第二個看到「已有人接了」 | 完成條件「兩人同時認領只有一人成功」；測試用兩條連線真的同時送出 |
| D42 | 「通知原排班者」做成站內顯示：原排班者的班表顯示誰會幫他去；別人求代班時，地圖頁「輪值」會出現數字 | 沿用 D21，站內通知不做推播 |

| D44 | 當天在該點記錄餵食，會自動把自己那一班標記完成（下午 2 點前先算早班）；也可以手動標記 | 少按一次；記錄餵食本來就是輪值要做的事 |
